# S11 阶段 5：断点恢复和补跑记录

日期：2026-06-10

## 目标

恢复完整交付任务时跳过已交付且文件有效的 job，只补缺失或失败的尺寸。

补跑要求：

```text
1. 恢复时识别 finalized job
2. 检查 final-package 中当前 job 三张最终图是否存在且尺寸正确
3. source-reuse target 缺失时可重新补齐
4. failed legil target 可补跑
5. “补跑此图”只补当前 job 缺失或失败 target
```

## 本阶段改动

### 1. finalized job 判定增加文件校验

文件：`src/routes/delivery.routes.js`

新增：

```text
isValidFinalOutputFile()
getExpectedFinalOutputPaths()
getMissingFinalTargetSizes()
```

`isDeliveryJobFinalized()` 不再只看状态，而是要求：

```text
1. job 内所有 target.status 都是 finalized
2. 每个 target 对应的 final JPG 存在
3. final JPG 尺寸与 targetSize 完全一致
```

因此如果 run 记录是 finalized，但用户手动删除了某个最终尺寸，恢复时不会跳过该 job。

### 2. 缺失 final 输出时只回退当前 target 的最终态

当某个 target 状态是 `finalized`，但最终 JPG 缺失或尺寸不对时，进入 job 闭环前会只回退该 target 的最终输出字段：

```text
target.status -> standardized 或 candidate_selected
target.finalPath -> ''
target.finalizedCandidates -> []
target.finalized -> null
target.logoPath -> ''
target.logoApplied -> false
```

这样后续会复用已有候选图或源图，重新走标准化和 finalize，而不是重新进入 Legil。

### 3. source-reuse 缺失可重新补齐

source-reuse target 仍然由阶段 1 的规则保护：

```text
generationMode === 'source-reuse' 或 reuseSource === true -> 不进入 Legil
```

如果删除 source-reuse target 的最终 JPG：

```text
恢复/补跑此图 -> 重新标准化源图 -> 重新加 LOGO -> 重新输出 final JPG
```

不会调用 Legil。

### 4. failed Legil target 可补跑

failed 的 Legil target 仍通过 `collectRunnableTargets()` 进入当前 job 的 Legil 队列。

如果只补跑当前 job：

```text
只收集当前 jobId 下 pending / failed / generating 或候选不足的 Legil target
source-reuse target 仍跳过
其它 finalized target 只走必要的后处理复用
```

### 5. “补跑此图”改为单 job 闭环

文件：`src/routes/delivery.routes.js`

新增：

```text
shouldCompleteJobDelivery()
```

当请求满足：

```text
processMode !== 'legil-only'
有 jobId
没有 targetSize
```

则后台走 `runDeliveryJobsClosedLoop()`，但只过滤执行当前 job。

这对应前端的“补跑此图”按钮：

```text
generateDeliveryJobCandidates(runId, jobId)
```

现在它会进行当前 job 的闭环补跑，而不是只生成候选图。

## 验收结论

```text
任务中断后重新开始，不重跑已 finalized job：通过
删除某个 job 的一个最终尺寸后，可补跑该 job：通过
source-reuse target 不因为补跑而进入 Legil：通过
failed legil target 可补跑：通过
“补跑此图”只补当前 job 缺失或失败 target：通过
```
