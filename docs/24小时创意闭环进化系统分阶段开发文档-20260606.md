## 1. 总体原则

### 1.1 一句话目标

```text
让系统能根据方向库和知识库持续自动生产、筛选、复盘和进化图片，最终达到“用户每周打开网站看一次周报和关键决策即可”。
```

### 1.2 第一性原则

| 原则 | 说明 |
| --- | --- |
| 先可控，再自动 | 所有自动决策先只读、再 shadow、再 canary、再 active |
| 先体验，再扩量 | 页面必须让人看懂当前状态、风险、下一步动作，否则不进入自动循环 |
| 先单轮，再多轮 | run-once 稳定后再进入监督式循环 |
| 先证据，再学习 | 每条规则、DNA、方向策略都要能追溯到资产、run 和反馈 |
| 先低风险默认值 | 未确认业务参数前使用保守默认策略 |
| 先验收脚本，再放权 | 自动化能力必须有脚本、接口或页面验收依据 |

### 1.3 四专家统一落地标准

每个阶段都必须同时满足四类标准，任何一层明显欠缺都不能算完成：

| 角色 | 必须回答的问题 | 必须落地的内容 | 不合格表现 |
| --- | --- | --- | --- |
| 10 年资深产品经理 | 这个阶段减少了什么人工？用户一周只看一次时能否完成判断？异常时怎么接管？ | 主路径、异常路径、接管路径、权限边界、决策项价值 | 只有功能列表，没有用户路径、异常态和决策价值 |
| 大厂资深 UI/UX 视觉设计师 | 页面是否深色高级、清晰、可扫读？状态、风险、主次是否一眼可见？ | 设计 token、组件规范、状态颜色、微交互、响应式布局 | 页面堆满按钮和表格，视觉压迫、层级混乱、缺少统一规范 |
| 一线资深前端工程师 | 页面是否组件化？状态、请求、轮询、错误、性能是否可维护？ | 模块边界、API client、懒加载、防抖节流、列表性能、可销毁轮询 | JS 全局变量继续膨胀、无 pending、无清理、无边界、无基础校验 |
| 中后台全栈架构师 | 接口和数据结构能否长期扩展？自动化决策能否追溯、回滚、迁移？ | route/service/store 分层、schema version、扩展字段、事件日志、幂等和迁移策略 | route 堆业务逻辑、字段临时拼接、状态不可追踪、后续功能难扩容 |

### 1.4 每阶段四层交付件

每个阶段的开发任务必须拆成四层交付件，避免“功能能跑但体验和架构欠债”：

| 层级 | 阶段交付件 | 说明 |
| --- | --- | --- |
| 产品体验 | 用户流程图、异常态清单、人工接管入口、默认策略 | 先明确用户怎么用、什么时候不用管、什么时候必须管 |
| UI 视觉 | 页面结构、深色设计规范、组件状态、响应式断点、微交互 | 先统一视觉语言，再开发页面，避免后期反复改样式 |
| 前端落地 | JS 模块、组件状态机、API 封装、性能策略、页面烟测 | 即使继续 vanilla JS，也按组件化和模块化方式组织 |
| 后端架构 | 接口契约、数据模型、service/store 分层、事件日志、扩展字段 | 后端不只满足当前页面，要为后续自治、反馈、归因预留空间 |

## 2. 全局产品体验规范

### 2.1 信息架构

后续不做整站大改，而是围绕现有页面做分层升级：

| 页面类型 | 页面 | 改造策略 |
| --- | --- | --- |
| 核心改造页 | 创意拓展 | 执行台：选题、队列、Prompt Gate、调度、产图、异常恢复、周报入口 |
| 核心改造页 | 知识库 | 大脑：方向库治理、参考图池、资产审核、反馈学习、Visual DNA、规则和健康度 |
| 可调整页 | 运行中心 | 状态仪表盘：全局健康、资源占用、当前 run、快捷启停、P0/P1 异常 |
| 内部标签页 | 周报决策、Visual DNA、方向健康度、闭环日志等 | 优先作为知识库/创意拓展里的二级标签页，不进入顶级导航 |
| 暂不改动页 | 批量产图、改尺寸、素材分析、任务方向池、配置 | 保持现有功能和流程；最多作为输入来源、跳转目标或只读状态来源 |

闭环系统的核心心智是：

```text
创意拓展负责跑起来。
知识库负责学起来。
运行中心负责看状态。
其它页面先稳定不动。
```

如果某个能力需要独立承载，优先新增为知识库/创意拓展内部标签页。只有内部标签页承载不了时，才考虑独立详情页，并且必须满足两个条件：

```text
1. 独立详情页服务于 24 小时闭环的复杂详情，不进入常规主导航。
2. 独立详情页不能要求改动批量产图、改尺寸、素材分析、任务方向池、配置页面的既有流程。
```

建议标签页归属：

| 标签页 | 放置页面 |
| --- | --- |
| 方向健康度 | 知识库 |
| Visual DNA | 知识库 |
| 周报决策 | 知识库优先，创意拓展放入口 |
| 闭环日志 | 创意拓展 |
| 异常恢复 | 创意拓展，运行中心只放摘要 |
| 资源占用 | 运行中心和创意拓展摘要 |

### 2.2 页面设计风格

这是生产工具，不是营销落地页。视觉风格应是：

```text
深色高级、冷静专业、高信息密度、强状态感、少装饰、可扫读。
```

设计要求：

- 使用深色中后台风格，但不能做成一片黑灰或单一蓝紫色。底色、边框、文本、状态色、强调色必须有稳定层级。
- 使用清晰的左侧或顶部功能导航，避免所有模块挤在一个超长页面。
- 页面模块使用全宽区域和紧凑面板，不做卡片套卡片。
- 卡片只用于资产图、方向条目、决策项、弹窗。
- 每个关键状态必须有颜色、图标、文字三重提示。
- 操作按钮使用清晰动词：`暂停`、`恢复`、`批准`、`延后`、`归档`、`进入 Safe Mode`。
- 高风险操作必须二次确认，并显示影响范围、预计影响对象和可回滚方式。
- 表格和列表必须支持搜索、筛选、分页或虚拟滚动。
- 移动端不追求完整管理能力，但必须能看状态、暂停、恢复、查看周报。
- 不使用大段说明文解释功能，功能应该通过布局、标签、状态和 tooltip 被理解。

### 2.3 深色高级风设计规范

建议在 P0 先定义一套轻量设计 token，后续所有页面统一使用：

| Token 类型 | 建议 |
| --- | --- |
| 背景 | `app-bg`、`surface-1`、`surface-2`、`surface-raised` 四层，不用纯黑大面积铺底 |
| 边框 | 使用低对比细边框区分区域，hover/selected 时只轻微增强 |
| 文本 | `text-primary`、`text-secondary`、`text-muted`、`text-danger`，避免灰度过近 |
| 状态色 | 运行、暂停、阻断、灰度、归档、成功、警告、错误必须全局一致 |
| 间距 | 4/8/12/16/24/32 的间距体系，避免随手写 margin |
| 圆角 | 中后台默认 6-8px，工具按钮和表格不要过度圆润 |
| 阴影 | 少量使用，只用于浮层、弹窗、悬停资产，不用大面积发光 |
| 动效 | hover、展开、保存成功等微交互控制在 120-180ms，不能影响操作效率 |

组件视觉要求：

- 主按钮只用于“开始/批准/保存/执行”等推进动作，危险按钮必须有红色或警告语义。
- 次级动作使用低强调按钮或图标按钮，常用工具类按钮优先使用图标加 tooltip。
- 表格行 hover、资产卡 selected、方向健康度变化必须有轻微状态反馈。
- 页面骨架屏优先于空白 loading，长任务显示进度、阶段和最近日志摘要。
- 页面自适应至少覆盖：`>=1440` 桌面、`1024-1439` 笔记本、`768-1023` 平板、`<768` 移动查看模式。
- 任何文本不能溢出按钮、卡片、表格单元格；长方向名、长提示词必须支持省略、换行或展开查看。

### 2.4 状态视觉规范

| 状态 | 颜色建议 | 用途 |
| --- | --- | --- |
| running | 绿色/青色 | 正常运行、任务进行中 |
| idle | 中性灰 | 空闲 |
| paused | 琥珀色 | 人工或系统暂停 |
| safe_mode | 蓝色 | 保守模式 |
| warning | 橙色 | 需要关注但不阻断 |
| blocked | 红色 | 阻断、P0、不可继续 |
| shadow | 紫色或靛色 | 影子模式，不执行 |
| canary | 青紫色 | 灰度验证 |
| active | 绿色 | 已启用 |
| archived | 灰色 | 归档 |

### 2.5 每个页面必须有的体验状态

每个新页面或模块都必须实现：

```text
loading
empty
ready
dirty/unsaved
saving
success
warning
error
disabled by policy
no permission / no config
```

如果页面只实现 happy path，不允许进入验收。

### 2.6 操作路径和异常态规范

产品层必须优先减少人工介入，把用户从“天天盯日志”变成“一周看一次关键决策”：

- 每个页面默认展示“最需要处理的 3-5 件事”，其余信息放到筛选、抽屉或详情页。
- 每个自动化任务都要有 `继续自动处理`、`暂停并接管`、`加入周报待决策` 三种出口。
- 高风险动作必须说明影响范围，例如影响哪些方向、多少张图、哪些队列、是否会触发 Legil 生成。
- 异常提示不能只写“失败”，必须包含：失败阶段、可能原因、系统已做的补救、用户可选动作。
- 能自动恢复的异常默认自动处理，只在超过重试上限、影响产出、涉及策略变更时打扰用户。
- 周报指挥台必须聚合本周需要人工确认的内容，避免用户进入多个页面逐个判断。
- 对于长期投放反馈，页面必须区分“短期自动评审结论”和“几个月后真实投放成熟结论”，避免误判。

## 3. 全局前端与中后台架构规范

### 3.1 当前技术约束

项目当前前端是 vanilla HTML/CSS/JS：

```text
public/index.html
public/js/*.js
public/css/*.css
```

短期继续沿用，不强行引入 React/Vue，避免改造成本过高。工程重点是模块化和状态收口。

### 3.2 新增前端模块建议

```text
public/js/autonomy-policy.js
public/js/reference-pool.js
public/js/auto-curator.js
public/js/direction-health.js
public/js/weekly-command-center.js
public/js/visual-dna.js
public/js/delivery-candidates.js
public/js/safe-mode.js
public/js/api-client.js
```

CSS 建议：

```text
public/css/autonomy.css
public/css/reference-pool.css
public/css/review-workbench.css
public/css/weekly-command-center.css
```

### 3.3 前端代码原则

- API 请求集中到轻量 `api-client.js`，避免每个模块手写 fetch、错误处理和 loading 状态。
- 每个功能模块只暴露 `init/render/load/refresh/destroy` 等少量入口，模块内部自己管理 DOM、状态和事件解绑。
- 复杂模块使用局部状态对象，不继续扩大零散全局变量。
- 轮询必须可停止，切页或销毁时清理 interval、AbortController 和事件监听。
- 表格和图片列表必须分页、懒加载或虚拟滚动，默认不一次性渲染大量图片。
- 图片缩略图使用懒加载，详情大图按需加载，避免打开页面即加载全部原图。
- 搜索、筛选、批量勾选、拖拽排序等高频交互必须做防抖或节流。
- 所有按钮点击要有 pending 态，避免重复提交。
- 所有危险操作前端和后端都要双重校验。
- 所有文案用业务语言，不暴露内部实现细节。
- 页面视觉验收必须包含桌面和移动端截图。

### 3.4 前端组件化拆分建议

即使短期不引入 React/Vue，也要按组件思路拆分 vanilla 模块：

| 组件/模块 | 职责 |
| --- | --- |
| `StatusBadge` | 统一渲染运行、暂停、阻断、灰度、归档等状态 |
| `MetricTile` | 统一渲染方向数、队列数、异常数、产出数等指标 |
| `ImageGrid` | 资产缩略图、懒加载、选中态、空态 |
| `DecisionList` | 周报决策项、批量批准、延后、拒绝 |
| `ConfirmDialog` | 高风险确认、影响范围、二次确认 |
| `Toast/Notice` | 成功、警告、错误、自动恢复提示 |
| `DrawerDetail` | 方向、资产、DNA、异常详情 |
| `FilterBar` | 搜索、筛选、排序、时间范围 |

组件化要求：

- 同一类状态、按钮、表格、图片卡不能在不同页面重复手写不同样式。
- 组件的输入数据必须稳定，例如 `status`、`title`、`subtitle`、`actions`、`meta`。
- 组件必须支持空态、加载态、错误态和禁用态。
- 新增内部标签页优先组合已有组件；只有内部标签页承载不了时才新增独立详情页。

### 3.5 中后台后端架构原则

- 不把大逻辑写在 route 中，route 只做入参校验、调用 service、返回标准响应。
- 核心服务独立到 `src/services/*`；如果暂时不重构目录，也要在现有文件内保持 route、service、store 的函数边界。
- 数据读写集中到 `src/stores/*` 或等价模块，避免多个 route 直接读写同一 JSON 文件。
- 写入 JSON 或 SQLite 前必须做 schema normalize，补齐默认字段，过滤未知危险字段。
- 每类核心数据必须有稳定 ID、`schemaVersion`、`createdAt`、`updatedAt`、`source`、`status`、`metadata` 或 `extensions` 预留字段。
- 自动动作必须通过 Policy Guard 检查，并记录允许或拒绝的原因。
- 关键状态变更必须写 event log，至少包含 `eventId`、`entityType`、`entityId`、`fromStatus`、`toStatus`、`actor`、`reason`、`createdAt`。
- 所有自动决策必须记录 reason、evidence、policyVersion，后续才能解释和回滚。
- 批量任务必须有幂等键，避免刷新页面、重试请求或服务重启导致重复生成。
- 长任务接口必须返回 job/run ID，前端通过状态接口查询，不依赖单个长请求挂住。
- 列表接口默认支持分页、筛选、排序和总数，避免后续数据量增长后重写接口。
- 错误响应必须统一结构：`code`、`message`、`stage`、`recoverable`、`suggestedAction`、`details`。
- 所有 LLM/Vision 相关新能力必须经 Lumos Winky 网关，不新增 Volcengine/Ark/Doubao 模型直连。

### 3.6 推荐接口响应结构

后续新增接口建议统一为：

```json
{
  "success": true,
  "data": {},
  "meta": {
    "requestId": "req_xxx",
    "schemaVersion": 1,
    "generatedAt": "2026-06-06T12:00:00.000Z"
  },
  "warnings": []
}
```

错误响应建议统一为：

```json
{
  "success": false,
  "error": {
    "code": "POLICY_BLOCKED",
    "message": "当前自治等级不允许自动启用该策略",
    "stage": "policy_guard",
    "recoverable": true,
    "suggestedAction": "加入周报待确认，或手动提升该方向的自治等级",
    "details": {}
  },
  "meta": {
    "requestId": "req_xxx",
    "schemaVersion": 1
  }
}
```

## 21. 每阶段四层通用验收清单

## 24. 补强开发项：一周一看自治保护层

### 24.10 第一批开发建议的微调

结合这些补强项，第一批最小开发建议从 P0-P3 稍微调整为：

```text
P0 基线收口与设计系统准备：同时建立缩略图 UI 规范。
P1 状态可信源与 Policy Guard：同时完成总开关、运行模式、为什么没跑解释系统。

```

第一批完成后的判断标准：

```text
系统知道自己当前允许做什么。
系统知道为什么没跑。
用户知道本周改了什么。
方向参考图可维护，且最多 3 张 active 图。
缩略图和图片列表不会拖慢页面。
失败开始被结构化记录，而不是只留在日志里。
```

第二批 P4-P6 建议同步加入：

```text

```

第三批 P7-P13 建议同步加入：

```text
P7 反馈学习与 Visual DNA 草稿：区分短期 AI good 和长期投放 winner。

P13 SQLite 与归档：补文件系统对账和缩略图缓存重建。
```
