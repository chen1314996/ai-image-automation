# 问题与解决方案 - 2026-05-14

## 问题 1：创意拓展表格明明有 1925 组提示词，页面只解析出 1475 组

### 现象

用户上传 `冰封末世创意方向拓展.xlsx` 后，创意拓展页面提示：

```text
已提取 1475 组提示词
```

但用户判断表格中应有：

```text
385 个方向 x 5 组提示词 = 1925 组提示词
```

### 排查过程

读取 Excel 工作簿后确认：

- 目标工作表：`新方向拓展表`
- 数据行数：385 个方向
- 提示词列：`提示词1` 到 `提示词5`
- 非空有效提示词单元格：1925

继续统计发现：

- 唯一提示词正文：1475
- 重复提示词单元格：450
- 重复行对：90

### 原因

`creative-table-parser.js` 中的解析器对提示词正文做了全表查重。

旧逻辑等价于：

```text
如果这段提示词正文以前出现过，则跳过。
如果没有出现过，则加入提示词列表。
```

因此系统不是漏读表格，而是把后续重复正文过滤掉了。

### 处理结果

经用户确认，创意拓展页面需要查重，因此保留“重复正文只保留第一次出现”的逻辑。

## 问题 2：解析日志没有说明查重前数量，容易误判为漏解析

### 现象

旧日志只显示：

```text
✅ 创意拓展表格解析完成：1475 组提示词
```

这无法解释为什么原始表格有 1925 个提示词单元格，页面却只有 1475 组。

### 解决方案

后端新增解析统计：

```js
parseStats: {
    totalPromptCount,
    dedupedPromptCount,
    duplicatePromptCount,
    duplicateRowPairs,
    duplicatePromptRows
}
```

前端根据统计结果输出不同日志。

### 有重复时

```text
✅ 创意拓展表格解析完成：共有1925 组提示词，查重后解析出1475组提示词，发现450处重复提示词，重复行示例：第7行与第2行有重复提示词；第8行与第3行有重复提示词
```

### 无重复时

```text
✅ 创意拓展表格解析完成：1925 组提示词
```

### 结果

用户可以一眼看到：

- 表格原始提示词总数。
- 查重后实际用于生成的提示词数量。
- 重复数量。
- 哪些行之间存在重复。

## 问题 3：重复行示例最初按提示词单元格展示，会重复出现同一行对

### 现象

同一对重复行通常有 5 个重复提示词列。如果直接展示前 5 个重复单元格，会变成：

```text
第7行与第2行有重复提示词
第7行与第2行有重复提示词
第7行与第2行有重复提示词
第7行与第2行有重复提示词
第7行与第2行有重复提示词
```

### 解决方案

后端增加 `duplicateRowPairs`，按“重复行对”聚合。

示例：

```json
{
  "sourceRow": 7,
  "duplicateOfRow": 2,
  "duplicatePromptCount": 5
}
```

前端优先使用 `duplicateRowPairs` 展示重复行示例。

### 结果

日志示例变为：

```text
第7行与第2行有重复提示词；第8行与第3行有重复提示词；第9行与第4行有重复提示词
```

信息密度更高，且不会重复刷同一句。

## 问题 4：量产页面无头模式启动时弹出 `chrome-headless-shell.exe` 终端窗口

### 现象

量产完整工作流启动后，桌面左侧出现黑色终端窗口，标题为：

```text
C:\Users\dd\AppData\Local\ms-playwright\chromium_headless_shell-1217\chrome-headless-shell-win64\chrome-headless-shell.exe
```

### 影响

- 打扰用户操作。
- 看起来像新开了一个终端窗口。
- 容易误以为自动化平台又弹出了浏览器或命令行。

### 原因

Playwright 在 Chromium 无头模式下，如果没有指定 `channel`，默认会使用：

```text
chromium-headless-shell
```

在 Windows 上，该可执行文件可能会被 Windows Terminal 承载并显示出来。

### 解决方案

在 `playwright-controller.js` 中，当 `useHeadless` 为 `true` 时设置：

```js
contextOptions.channel = 'chromium';
```

这样无头模式改用完整 Chromium：

```text
chromium-1217\chrome-win64\chrome.exe
```

而不是：

```text
chromium_headless_shell-1217\chrome-headless-shell.exe
```

### 验证

临时启动 Playwright 验证：

```text
headless + channel: chromium
```

结果：

```text
processNames: chrome.exe
hasHeadlessShell: false
```

### 注意

当天排查时量产工作流正在运行，所以未强制重启服务。当前运行中的旧浏览器进程仍可能是 `chrome-headless-shell.exe`，但后续新启动会使用新逻辑。

## 问题 5：正在运行的量产任务不应被修复过程打断

### 现象

排查弹窗时，`/api/health` 显示量产完整工作流正在运行：

```text
workflow.isRunning = true
phase = generating_in_legil
browserMode = headless
```

### 风险

如果强制重启服务或关闭浏览器，会中断正在生成的图片任务。

### 处理

- 不重启服务。
- 不关闭浏览器。
- 不结束 `chrome-headless-shell.exe`。
- 只隐藏承载窗口 `WindowsTerminal.exe`。

### 结果

当前任务继续运行，用户桌面上的黑色窗口被隐藏。
