# 问题与解决方案 - 2026-05-31

## 问题 1：跨天运行后，失败状态需要能被继续理解

### 现象

Legil 三尺寸交付运行跨过 5/30 到 5/31 后，错误截图和运行状态仍在持续产生。只看单次请求结果无法还原全链路进度。

### 原因

三尺寸交付是长流程，真实页面任务可能跨小时甚至跨天。状态如果只存在内存或日志中，复盘和继续都会很困难。

### 解决方案

- 将 run/job/target/candidate 状态落盘到 JSON。
- 保留每个 target 的更新时间、错误信息和候选列表。
- 后续在页面上提供历史 run 读取和继续能力。

### 结果

明确了 delivery run 本地持久化是 S10 的核心能力之一。

## 问题 2：错误截图多，但缺少结构化归因

### 现象

截图能够证明失败发生，但无法自动告诉系统失败属于哪种类型。

### 原因

截图是证据，不是结构化状态。需要代码把失败发生阶段、targetSize、prompt、候选序号写进 run 状态。

### 解决方案

- 错误截图继续保存。
- target 状态中补充 `error` 字段。
- 文件名中保留 runId/prompt/时间戳，方便人工定位。
- 后续可增加错误类型枚举。

### 结果

为后续 `retry-target` 和前端失败提示提供依据。

---

## 问题 3：源码日报需要避免“运行产物膨胀”

### 现象

5/31 文件变更主要来自 browser_data 和 runtime，而不是人工维护源码。

### 原因

真实 Playwright 运行会持续改写浏览器状态和缓存文件。

### 解决方案

- 日报中单独列出运行产物。
- 代码变更记录只记录真正需要维护的源码、文档和测试。
- 后续通过 `.gitignore` 和提交策略控制运行数据边界。

### 结果

5/31 报告口径保持为“观察复盘”，不夸大交付内容。
