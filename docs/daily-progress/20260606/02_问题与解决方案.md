# 问题与解决方案 - 2026-06-06

## 问题 1：系统能力很多，但缺少新阶段边界

### 现象

项目已经包含批量产图、改尺寸、三尺寸交付、自动创意、素材分析、表格 prompt、知识库和飞书控制。如果直接推进 24 小时闭环，容易影响现有工具。

### 原因

前期能力按需求逐步扩张，页面入口和职责边界开始变复杂。

### 解决方案

- 新增 24 小时闭环新版方案。
- 明确独立工具保护边界。
- P0 不重做主流程，只收口运行中心、创意拓展、知识库。

### 结果

新阶段有了清晰入口和不碰边界，降低了误改现有工具的风险。

---

## 问题 2：Agent 生成方向可能抽象、重复或不可生产

### 现象

自动创意中仍有 agent_failed 和修复需求，说明仅靠模型一次输出不够稳定。

### 原因

模型容易输出“氛围感、主题拓展”等抽象方向，或只做同义词改写，缺少具体事件机制和视觉抓手。

### 解决方案

- 新增方向计划 Gate。
- 对候选方向做评分。
- 对未达标方向进入 repair loop。
- 更新 Agent 项目设定和 prompt 设置。

### 结果

方向生成从“生成后直接进 prompt”变成“先规划、评分、修复、再生成”，为提高有效产图率打基础。

---

## 问题 3：前端状态分散，不利于运行中心

### 现象

状态请求、轮询、运行中心展示和诊断提示散落在不同页面逻辑里。

### 原因

早期页面集中在 `public/index.html` 和若干功能 JS，随着页面增多，全局状态越来越复杂。

### 解决方案

- 拆出 `api-client.js`。
- 拆出 `status-poller.js`。
- 拆出 `run-center.js`。
- 拆出 `autonomy-diagnostics.js`。
- 新增 `autonomy.css`。

### 结果

P0 阶段开始把运行中心和诊断视图模块化，后续更容易继续拆前端。

---

## 问题 4：长跑需要可信诊断，而不是只看日志

### 现象

24 小时运行时，单看日志难以判断系统是否健康、队列是否阻塞、资产是否积压。

### 原因

运行状态分布在 serviceStatus、schedulerState、targetQueue、lastRun、Legil resume 和 knowledge counts 中。

### 解决方案

- 新增 `/api/creative-auto/diagnostics`。
- P0 诊断统一返回：

```text
serviceStatus
schedulerState
targetQueue
lastRun
legilResume
knowledgeCounts
policySummary
warnings
```

### 结果

运行中心可以显示系统阶段、健康摘要和 P0/P1 警告，为后续自动化守护打基础。
