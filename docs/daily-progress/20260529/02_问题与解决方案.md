# 问题与解决方案 - 2026-05-29

## 问题 1：旧“改尺寸”概念无法覆盖真实交付流程

### 现象

旧流程把图片比例处理叫“改尺寸”，容易让人理解为本地裁切、缩放或简单压缩。但真实业务要求是：

- 每张 OK 图要生成 800x800、1280x720、1080x1920 三个尺寸。
- 三个尺寸要重新构图和适配，不是简单拉伸。
- 每个尺寸要有 2-4 张候选图。
- 人工从候选中挑最终图。
- 最终图要加 LOGO、重命名、按图打包。

### 原因

“改尺寸”是技术动作，“三尺寸交付”是业务流程。继续沿用旧入口会让量产候选图、最终交付图、本地标准化、AI 图生图混在一起。

### 解决方案

- 新版 S10 明确拆成两段流水线：
  - 自动创意量产。
  - OK 图三尺寸交付。
- 页面上新增“三尺寸交付”入口。
- 旧即梦改尺寸从主流程移除，三尺寸适配主流程只保留 Legil。
- 本地标准化作为三尺寸交付内部步骤，不再作为主流程含义。

### 结果

业务边界清楚了：量产只负责探索和出候选，三尺寸交付只处理人工挑出的 OK 图。

## 问题 2：不能自动把所有量产图送进交付后处理

### 现象

量产输出中会有大量质量不一的候选图。如果系统自动把所有图都送到三尺寸处理，会造成成本、时间和人工选择压力大幅增加。

### 原因

量产阶段是探索，交付阶段是确认后的制作。两者质量门槛不同。

### 解决方案

- 约定 OK 图交接方式为“人工复制”。
- 用户从量产输出中挑 OK 图，复制到新的三尺寸交付输入文件夹。
- 系统只扫描这个 OK 图文件夹，不破坏原量产目录。

### 结果

交付后处理只处理人工确认过的 OK 图，成本和任务数量可控。

## 问题 3：每张图需要同时追踪三个尺寸、多个候选和最终选择

### 现象

单张 OK 图不再只有一个输出，而是：

```text
1 张原图
3 个目标尺寸
每个尺寸 2-4 张候选
每个尺寸 1 张最终选中图
```

如果只用扁平文件列表，很难知道哪个候选属于哪个尺寸、哪个 job、哪个 run。

### 原因

交付流程是层级任务：run -> job -> target -> candidates -> selected/final。

### 解决方案

- 新增 delivery run 数据结构。
- 每个输入文件夹生成或复用一个 run。
- 每张 OK 图生成一个 job。
- 每个 job 固定三个 target：

```text
800x800
1280x720
1080x1920
```

- 每个 target 独立记录：
  - status
  - aspectRatio
  - candidateCount
  - candidates
  - selectedCandidateId
  - standardizedPath
  - finalPath
  - error

### 结果

三尺寸任务可追踪、可继续、可重跑、可在页面上按 job 和 target 展示。

## 问题 4：AI 候选图仍需要本地标准化

### 现象

Legil 图生图可以做构图适配，但输出图片未必正好是交付要求的精确像素和体积。

### 原因

AI 生图输出受平台参数和页面行为影响，最终交付仍需要本地确定性处理。

### 解决方案

- 新增 `standardizeImageToTarget()`。
- 本地读取候选图，按目标尺寸 cover 标准化。
- 输出 JPG。
- 控制最大体积 `390KB`。
- 标准化后再次读取图片尺寸，确保像素精确。

### 结果

当前测试已验证选中候选可标准化为精确 `800x800`，且小于 390KB。后续同逻辑覆盖 1280x720 和 1080x1920。

## 问题 5：后处理派生图需要追溯回原始资产

### 现象

如果图片经过重命名、标准化、加 LOGO、打包后不写回资产追溯，就很难知道最终交付图来源于哪个 run、哪个 prompt、哪张原始图。

### 原因

交付后处理会生成多级派生文件，仅靠文件名不足以完整追踪来源。

### 解决方案

- 新增 `postprocess-trace` 服务。
- 准备后处理输入时写 manifest。
- 记录操作结果时根据 manifest 匹配回原始 asset。
- 在 asset 中写入 `postprocess.derivatives`。

### 结果

重命名等后处理结果可以保留 `sourceAssetId`、`sourceRunId`、`sourcePromptId` 和输出路径。

## 问题 6：S10 页面必须同时支持“仅候选生成”和“完整交付”

### 现象

第一版可能先只跑 Legil 候选生成，但完整业务还包括 LOGO、重命名和打包。如果页面只做一种模式，会影响分阶段验收。

### 原因

S10 是多阶段能力，不能等所有环节完成后才提供可操作页面。

### 解决方案

- 页面加入 `deliveryProcessMode`：
  - `legil-only`
  - `full-delivery`
- `legil-only` 模式隐藏或降级 LOGO、命名等后续区域。
- `full-delivery` 模式保留完整交付配置。
- 当前 `finalize` 接口先返回占位提示，明确 LOGO、重命名和打包后续接入。

### 结果

S10 可以先验收候选生成和标准化，再继续接最终交付步骤。
