# 问题与解决方案 - 2026-06-03

## 问题 1：历史输出文件名混入技术元数据，影响交付可读性

### 现象

历史创意输出文件名中经常包含 runId、序号、ref/prompt、版本号、日期时间等技术信息，业务标签和画面标题不够清楚。

### 原因

前期文件名主要服务于自动化保存和追溯，优先保证唯一性；随着资产进入交付和人工筛选阶段，文件名需要更强调业务标签、内容标题和目标尺寸。

### 解决方案

- 新增 `source-business-name.js` 提取业务命名段。
- 修改 `image-renamer.js`，重命名时优先沿用解析出的业务名。
- 新增 `fix-creative-output-names.js` 批量修复历史输出。
- 同步修复 assets 和 runs JSON 中的文件名、路径和标签元数据。

### 结果

本轮完成 2097 个文件的主批量 apply，并完成 16 个残留项 apply，最终 dry-run 为 0。

## 问题 2：批量重命名容易误伤目录或造成文件冲突

### 现象

一次性处理 2000 多个文件，如果没有安全校验，可能误重命名非目标目录文件，或因目标文件名重复造成覆盖风险。

### 原因

历史文件名规则不完全一致，同一目录里可能存在旧命名、prompt 文本、图片、已修复文件和残留项。

### 解决方案

- `fix-creative-output-names.js` 默认只 dry-run。
- apply 前会：
  - 校验路径必须在目标目录内。
  - 对 oldName 去重。
  - 对 newName 查重。
  - 如果目标文件已存在则跳过。
  - 使用临时文件名两段式 rename。
- 每次运行生成 `data/rename-reports/*.json` 报告。

### 结果

今日 2097 个主批量和 16 个残留项 apply 的 skipped 均为 0，过程可追溯。

## 问题 4：Creative Agent 表格输出不适合自动化主链路

### 现象

Markdown/Excel 表格适合人工看，但作为后台自动创意、Prompt Gate 和 Legil 队列的主契约不够稳定。

### 原因

表格解析容易受列名、顺序、换行和模型输出格式影响；同时当前目标是让 Agent 直接输出候选方向和 prompt，程序再负责审核、入库和执行。

### 解决方案

- Creative Agent 输出改为 JSON-first。
- 顶层字段要求 `candidateDirections`。
- 每个方向带八维创意标签和 prompts。
- 程序直接抽取 promptItems 进入质量检查和后续流程。
- Excel/workbook 保留为展示/导出层，而不是主自动化契约。

### 结果

Agent 输出与自动化链路更贴合，后续可直接连接 Prompt Gate 和 Legil 队列。

## 问题 5：LLM 调用需要兼容新模型参数和网络波动

### 现象

不同模型可能使用不同 token 参数，网络调用也可能出现 AggregateError、timeout、socket hang up 等临时问题。

### 原因

项目已经有多个 LLM 调用点，且都需要走 Lumos Winky；如果每个模块各写一套调用逻辑，错误处理和兼容性会不一致。

### 解决方案

- 在 Creative Agent 调用中增加重试和错误脱敏。
- 对 `gpt-5.5` 类模型使用 `max_completion_tokens`。
- 对可重试网络错误做一次延迟重试。
- 素材分析、任务工作簿、Prompt 转译、反馈学习继续统一到 Winky 配置。

### 结果

LLM 调用稳定性提升，后续仍需要继续检查是否还有历史 Doubao/Ark/Volcengine 直连残留。
