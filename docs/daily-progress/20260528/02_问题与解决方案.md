# 问题与解决方案 - 2026-05-28

## 问题 1：本地运行数据、样例数据和代码文件边界不清楚

### 现象

工作区中出现了多类本地数据：

```text
data/creative-knowledge/
data/material-analysis/
data/acceptance-*.png
data/tmp-*.xlsx
public/generated/
sucai/
```

如果不区分来源，后续提交时容易把运行产物、真实素材、验收截图和临时工作簿混入代码。

### 原因

创意知识库、素材分析、页面验收和提示词池导出都会生成本地文件，其中有些是源数据，有些是运行产物，有些只是临时证据。

### 解决方案

- 将明确属于运行产物的目录和文件写入 `.gitignore`。
- `sucai/` 暂不全局忽略，因为它仍是当前项目的方向种子和素材数据入口。
- 在 S7 验收记录中把每类路径的策略写清楚。
- 新增 `scripts/s7-acceptance-check.js`，检查 `.gitignore` 中是否存在这些边界规则。

### 结果

本地数据边界清楚了，后续提交前只需要单独决定 `sucai/` 是否整理为脱敏样例即可。

## 问题 2：接口文档落后于页面和路由

### 现象

创意知识库、运行一次自动创意、素材分析和改尺寸续跑已经有大量新增接口，但接口清单没有完全同步。

### 原因

S0-S6 开发过程中先完成了服务和页面，文档没有在同一节奏补齐。若直接进入后续阶段，页面按钮、后端路由和验收脚本之间会难以对照。

### 解决方案

- 补齐 `docs/接口清单.md`：
  - `/api/creative-knowledge/*`
  - `/api/creative-auto/*`
  - `/api/material-analysis/*`
  - `/api/resize/resume`
  - `/api/resize/resume/clear`
- S7 静态验收脚本检查关键接口是否既写入文档，又能在 route 文件中找到。

### 结果

S7 关心的核心接口文档已经与当前代码对齐。

## 问题 3：只跑服务级测试不能证明真实链路可用

### 现象

此前已有大量脚本测试，但真实外部平台仍可能存在问题：

- Winky 鉴权或图文格式问题。
- Legil 页面选择器或保存行为问题。
- 页面布局在桌面和移动端下遮挡。
- 飞书桥接或通知配置不可用。

### 原因

自动化脚本和 stub 可以验证合同，但不能替代真实平台调用和真实浏览器页面。

### 解决方案

- 将 S7 定义为“当前能力收口与真实验收”阶段。
- 除服务级脚本外，补跑真实链路：
  - Winky 图文请求。
  - 素材视觉识别。
  - run-once 到 Legil 出图和资产入库。
  - Legil 改尺寸中断和继续。
  - 页面烟测。
  - 飞书通知测试。
- 失败原因必须记录，不用 stub 伪装通过。

### 结果

S7 真实链路大部分通过，剩余风险被明确记录为即梦续跑未补跑、run 详情资产入库汇总字段未直接回显。

## 问题 4：素材分析经验如果直接写方向库，会污染正式方向

### 现象

素材分析能发现优秀素材和风险素材，但这些信息既有长期价值，也可能包含一次性噪声。如果直接写入正式方向库，会造成方向库膨胀和质量失控。

### 原因

素材分析经验与正式方向不是同一类数据。正式方向需要直观、可复刻、可被人工确认；素材分析经验更适合作为策略记忆和 Prompt Gate 避坑依据。

### 解决方案

- 新增素材经验池 `material-learnings.json`。
- 负向素材写入 `creative-memory.json`，作为 Prompt Gate 避坑规则。
- 方向草稿只作为候选，不直接进入正式方向库。
- 所有沉淀和生成草稿动作都要求人工确认。

### 结果

S8 的经验沉淀路径更稳：经验可以影响自动选题和 Prompt Gate，但不会自动污染正式方向库。

## 问题 5：飞书同步需要先只读，不能一开始就双向写回

### 现象

后续需要从飞书团队底表获取方向、TOP 素材和参考图，但如果一开始就做写回，会把本地试验状态同步到团队表，风险较高。

### 原因

飞书表是团队共享数据源，本地知识库则包含自动生成、人工筛选、禁用和实验性状态，两者可信等级不同。

### 解决方案

- 先实现 `feishu-sync` 只读服务。
- 支持 preview，先看新增、更新、忽略数量。
- 同步时保留本地人工状态。
- 记录 `feishu-cache.json` 和 `knowledge-operations.json`，便于回溯。

### 结果

飞书同步基础可测，且不会覆盖本地人工决策。后续再单独设计写回规则。

## 问题 6：PowerShell 手工请求中文路径时可能编码错误

### 现象

S7 真实 Winky 验收中发现，PowerShell 手工请求如果没有显式 UTF-8，中文绝对路径可能被转成 `??`。

### 原因

命令行请求体编码与 Node/浏览器前端 fetch 的 UTF-8 行为不同。

### 解决方案

- 验收记录中明确此问题只影响命令行手工请求方式。
- 后续命令行验收建议显式发送 UTF-8 body 或使用相对路径。
- 前端 fetch 路径不应受此问题影响，但仍建议真实页面再验收一次。

### 结果

问题被记录为验收注意项，不阻塞 S7 通过。
