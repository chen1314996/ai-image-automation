# 问题与解决方案 - 2026-05-30

## 问题 1：Legil 真实运行中错误截图数量较多

### 现象

`runtime/legil-error-screenshots/` 在 5/30 持续产生截图，说明三尺寸交付真实运行中存在页面等待、出图检测或保存阶段的不稳定情况。

### 原因

Legil 是外部网页平台，页面状态、生成耗时、按钮可用性、输出渲染和保存路径都可能波动。S10 第一版如果只按成功路径设计，很难支撑长时间量产。

### 解决方案

- 保留错误截图作为定位证据。
- 在 delivery target 维度记录失败原因，而不是只记录 run 失败。
- 支持单个 target 重跑，避免一处失败导致整张 OK 图重来。
- 将停止/继续能力纳入 S10 基础流程。

### 结果

明确了 S10 后续加固重点：从“能启动候选生成”升级为“能解释失败并恢复运行”。

## 问题 2：运行产物和源码改动容易混在一起

### 现象

5/30 的主要新增内容集中在 runtime 截图、delivery run JSON 和浏览器状态，不是源码功能开发。

### 原因

真实跑数会产生大量机器文件，如果日报只按文件时间线写，容易误判为代码交付。

### 解决方案

- 日报中明确标记“运行产物”和“源码变更”。
- `runtime/`、`browser_data/`、`data/*/runs` 默认作为运行证据，不作为源码成果。
- 代码变更记录中单独写“本日未记录大规模源码变更”。

### 结果

5/30 被定义为 S10 真实验收观察日，日报口径更准确。

---

## 问题 3：三尺寸交付需要更细粒度的状态恢复

### 现象

单张 OK 图会拆成三个尺寸 target，每个 target 又有多个候选。只要其中一个尺寸失败，就需要能定位到具体尺寸并重跑。

### 原因

真实交付不是线性单任务，而是层级任务：

```text
run -> job -> target -> candidate -> selected/final
```

### 解决方案

- 保留 target 级状态。
- 对每个 target 记录候选、错误、更新时间和标准化结果。
- 前端按 job/target 展示状态，便于人工介入。

### 结果

为 6/1 继续完善 delivery store、standardize、finalize 和 route 契约提供了清晰方向。
