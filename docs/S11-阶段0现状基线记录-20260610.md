```text

```

## 2. 测试输入覆盖

脚本会临时生成四类 OK 图：

| 文件名 | 尺寸 | 比例用途 |
| --- | --- | --- |
| `ok_square_1x1.png` | `800x800` | 后续源图复用 `800x800 / 1:1` 的基准 |
| `ok_landscape_16x9.png` | `1280x720` | 后续源图复用 `1280x720 / 16:9` 的基准 |
| `ok_portrait_9x16.png` | `1080x1920` | 后续源图复用 `1080x1920 / 9:16` 的基准 |
| `ok_other_4x3.png` | `1000x750` | 后续不命中三目标比例、全部走 Legil 的基准 |

同时生成三个 LOGO 模板：

```text
logo_800x800.png
logo_1280x720.png
logo_1080x1920.png
```

## 3. 当前锁定的稳定合同

### 3.1 scan 合同

脚本确认：

```text
1. 每张 OK 图创建一个 delivery job
2. run.targetSizes 保持固定顺序：
   - 800x800
   - 1280x720
   - 1080x1920
3. 每个 job 都有三个 target
4. target.size 和 target key 一致
5. target.aspectRatio 与目标比例表一致
6. sourceImage.fileName、extension、fileSize、sourceKey 会落盘
7. readImageDimensions() 能读取四类测试 OK 图的真实宽高
8. run JSON 会写入 data/delivery-postprocess/runs
9. getLatestRun(inputFolder) 能找回本次扫描 run
```

### 3.2 标准化合同

脚本确认：

```text
1. 候选图可以标准化为三个目标尺寸
2. 输出为 JPG
3. 输出尺寸精确：
   - 800x800
   - 1280x720
   - 1080x1920
4. 输出体积小于 390KB
5. buildStandardizedOutputPath() 的命名仍是：
   {baseName}_{targetSize}.jpg
```

### 3.3 最终交付合同

脚本确认单个完整 job 的最终输出：

```text
1. 三个 target 都已 standardized 时，finalizeDeliveryRun() 可输出三张最终图
2. final-package 目录结构保持：
   final-package/{job.folderName}/{job.baseName}_{targetSize}.jpg
3. 最终图尺寸精确
4. 最终图体积小于 390KB
5. target.status 会进入 finalized
6. job.status 会进入 finalized
7. job.postprocess.finalPackageFolder 会记录最终文件夹
```

## 4. 本阶段刻意不锁死的旧行为

阶段 1 会引入源比例复用，所以阶段 0 的保护脚本不锁死这些马上要改变的行为：

| 旧行为 | 不锁死原因 |
| --- | --- |
| 所有 target 初始都是 `pending` | 阶段 1 后，匹配源比例的 target 会变成 `candidate_selected` 或 ready 状态 |
| 所有 target 都按统一 candidateCount | 阶段 1 后，source-reuse target 固定 1 个候选，Legil target 保持页面配置 |
| 全 run 后处理作为唯一主路径 | 阶段 3 后，完整交付会按 job 闭环执行 |
| `finalizeDeliveryRun()` 只能全 run 遍历 | 阶段 4 会增加 jobId 过滤能力 |

这样做的目的：保护真正稳定的交付合同，同时不阻挡后续 S11 的目标改造。
