# S11：源比例复用与逐张闭环三尺寸交付分阶段开发方案

> 文档日期：2026-06-10  
> 项目目录：`C:\Users\dd\Desktop\项目`  
> 适用范围：在现有 S10 三尺寸交付基础上，优化 OK 图改尺寸、加 LOGO、重命名、打包流程。  
> 核心目标：源 OK 图已经匹配目标比例时，默认跳过 Legil 生成，直接复用源图进入后处理；完整交付模式按单张 OK 图闭环执行，完成一张交付一张，再处理下一张。

---

## 1. 背景和问题

当前三尺寸交付流程默认把每张 OK 图的三个目标尺寸都送去 Legil 生成候选：

```text
每张 OK 图
  -> 800x800 / 1:1 送 Legil
  -> 1280x720 / 16:9 送 Legil
  -> 1080x1920 / 9:16 送 Legil
  -> 所有 OK 图全部生成完
  -> 统一标准化
  -> 统一加 LOGO
  -> 统一重命名
  -> 统一输出 final-package
```

这个流程有两个明显浪费点：

| 问题 | 影响 |
| --- | --- |
| 源 OK 图本身已经是某个目标比例，仍然重新调用 Legil | 浪费时间、额度和平台资源，也增加失败概率 |
| 一次把所有图片的 AI 适配都做完后才进入后处理 | 中途失败时，前面已经生成好的图还没有形成完整交付包，恢复和排查都不够直观 |

典型例子：

```text
源 OK 图比例：1:1
目标尺寸：800x800、1280x720、1080x1920
```

实际只需要 Legil 生成：

```text
1280x720 / 16:9
1080x1920 / 9:16
```

`800x800 / 1:1` 这一张应该直接复用源 OK 图，再通过本地标准化、加 LOGO、重命名、打包进入最终交付。

---

## 2. 已确认业务规则

| 规则 | 说明 |
| --- | --- |
| 源图复用判断 | 只按比例判断，不要求源图像素刚好等于目标尺寸 |
| 源图复用范围 | 仅复用匹配比例的目标尺寸，例如源图是 `1:1` 时只复用 `800x800` |
| 源图复用后处理 | 完整交付模式下，复用源图也必须走同一套标准化、压缩、加 LOGO、重命名、输出流程 |
| 默认行为 | 源图比例匹配时默认跳过 Legil，不需要用户每次确认 |
| 交付粒度 | 完整交付模式按单张 OK 图闭环处理，当前图三尺寸齐备后立即后处理和输出，再进入下一张 |
| 最终交付要求 | 每张 OK 图最终仍然输出 `800x800`、`1280x720`、`1080x1920` 三个尺寸 |
| 候选数量 | 源图复用 target 固定 1 张候选并默认选中；Legil target 按页面配置生成候选 |
| 强制 AI 适配 | 第一版不做前端开关；默认跳过匹配比例即可 |

## 3. 新版流程定义

### 3.1 流程总览

新版完整交付流程：

```text
扫描 OK 图文件夹
  -> 读取每张 OK 图真实宽高
  -> 判断源图比例
  -> 为每张 OK 图建立 delivery job
  -> 每个 job 固定包含三个 target
     - 800x800 / 1:1
     - 1280x720 / 16:9
     - 1080x1920 / 9:16
  -> 源图比例命中的 target 标记为 source-reuse
  -> 源图比例未命中的 target 标记为 legil

开始完整交付
  -> 按 OK 图顺序逐张处理
  -> 当前 job 内只对 legil target 调用 Legil
  -> source-reuse target 直接使用源 OK 图作为候选
  -> 当前 job 三个 target 都有候选后立即标准化
  -> 当前 job 标准化完成后立即加 LOGO、重命名、输出 final-package
  -> 当前 job 完成后进入下一张 OK 图
```

### 3.2 单张 OK 图闭环

```text
处理第 N 张 OK 图
  1. 读取 job 状态
  2. 确认三个 target
  3. source-reuse target：
     - 不调用 Legil
     - 使用源 OK 图作为唯一候选
     - 默认选中
  4. legil target：
     - 调用 Legil 图生图
     - 保存候选图
     - 自动选用可交付候选
  5. 当前 job 三尺寸齐备
  6. 标准化当前 job 的三个 target
  7. 加对应尺寸 LOGO
  8. 按命名规则输出当前 job 的最终文件夹
  9. job 标记 finalized
  10. 进入下一张 OK 图
```

### 3.3 具体示例

源 OK 图：

```text
GOFCNIM001_角色_冰洞孤童.png
源图尺寸：1024x1024
源图比例：1:1
```

执行计划：

| 目标尺寸 | 比例 | 处理方式 |
| --- | --- | --- |
| `800x800` | `1:1` | 源图复用，跳过 Legil |
| `1280x720` | `16:9` | Legil 生成 |
| `1080x1920` | `9:16` | Legil 生成 |

最终输出：

```text
final-package/
  GOFCNIM001_角色_冰洞孤童/
    GOFCNIM001_角色_冰洞孤童_800x800.jpg
    GOFCNIM001_角色_冰洞孤童_1280x720.jpg
    GOFCNIM001_角色_冰洞孤童_1080x1920.jpg
```

其中 `800x800` 来自源 OK 图，但仍然经过本地标准化、压缩、加 LOGO 和最终命名。

## 4. 源比例识别规则

### 4.1 目标比例表

| 目标尺寸 | 目标比例 | 数值 |
| --- | --- | --- |
| `800x800` | `1:1` | `1.0` |
| `1280x720` | `16:9` | `1.7777777778` |
| `1080x1920` | `9:16` | `0.5625` |

### 4.2 判断方式

主判断必须读取图片真实宽高，文件名只可作为辅助信息，不作为主要依据。

建议容差：

```text
ratioTolerance = 0.02
```

判断公式：

```text
actualRatio = width / height
targetRatio = targetWidth / targetHeight

如果 abs(actualRatio - targetRatio) / targetRatio <= ratioTolerance
则认为源图匹配该目标比例
```

示例：

| 源图尺寸 | 识别结果 | 复用目标 |
| --- | --- | --- |
| `1024x1024` | `1:1` | `800x800` |
| `800x801` | `1:1`，容差内 | `800x800` |
| `1920x1080` | `16:9` | `1280x720` |
| `1280x721` | `16:9`，容差内 | `1280x720` |
| `1080x1920` | `9:16` | `1080x1920` |
| `1000x1500` | 不匹配三种目标比例 | 三个尺寸都走 Legil |

### 4.3 多重命中处理

正常情况下不会多重命中。若因为异常宽高或容差导致多个比例都命中，选择误差最小的比例。

## 6. 后端开发方案

### 6.1 关键文件

| 文件 | 调整内容 |
| --- | --- |
| `src/services/delivery-postprocess/store.js` | 扫描 OK 图时读取源图尺寸，识别源比例，初始化 source-reuse target |
| `src/routes/delivery.routes.js` | 将完整交付从 target 大队列调整为 job 闭环队列 |
| `src/services/delivery-postprocess/standardize.js` | 保持现有能力，确保 source-reuse candidate 可作为标准化输入 |
| `src/services/delivery-postprocess/finalize.js` | 增加或完善按 job finalization 的能力 |
| `src/services/image-renamer.js` | 复用 `readImageDimensions()` 读取图片宽高 |

### 6.2 scan 阶段调整

扫描 OK 图时执行：

```text
1. listOkImages(inputFolder)
2. 对每张图片读取真实宽高
3. 计算源图比例
4. 找到匹配的目标尺寸
5. 创建 delivery job
6. 对匹配目标创建 source-reuse target
7. 对未匹配目标创建 legil target
8. 保存 run
```

建议新增函数：

```js
function detectSourceMatchedTargetSize(imageDimensions, targetSizes) {}
function createSourceReuseTarget(size, image, dimensions, existingTarget) {}
function createLegilTarget(size, candidateCount, dimensions, existingTarget) {}
```

### 6.3 collectRunnableTargets 调整

现有 `collectRunnableTargets()` 已经会跳过 `candidate_selected`、`candidates_ready`、`standardized`、`logo_applied`、`finalized` 状态。

需要确认：

```text
source-reuse target 的 status 必须是 candidate_selected 或 candidates_ready
```

这样它天然不会进入 Legil 队列。

如果后续支持强制重跑，则需要：

```text
force=true 且 target.generationMode=source-reuse 时，第一版仍不强制重跑
```

第一版默认不做强制 AI 适配。

### 6.4 完整交付执行器调整

当前完整交付倾向于：

```text
collect all runnable targets
  -> run all target generation
  -> standardize whole run
  -> finalize whole run
```

新版完整交付改成：

```text
for each job in run.jobs:
  if job finalized:
    continue

  mark job running

  ensure source-reuse targets ready

  for each target in job.targets:
    if target generationMode is source-reuse:
      continue
    if target needs generation:
      run Legil for current target

  if current job has enough candidates:
    standardize current job
    finalize current job
    mark job finalized
  else:
    mark job failed or partial_finalized

  save run
  continue next job
```

建议新增函数：

```js
async function runDeliveryJobClosedLoop(run, job, options) {}
async function runDeliveryJobsClosedLoop(runId, options) {}
function jobHasAllRequiredCandidates(job, targetSizes) {}
function shouldSkipFinalizedJob(job, targetSizes) {}
```

### 6.5 job 级标准化

现有 `standardizeDeliveryRun(runId, body)` 已支持 `body.jobId` 过滤。

需要在完整交付执行器中按当前 job 调用：

```js
await standardizeDeliveryRun(run.runId, {
  ...options,
  jobId: job.jobId
});
```

要求：

```text
source-reuse target 的 candidate.filePath 指向源 OK 图
standardizeImageToTarget() 能直接读取源 OK 图并输出目标尺寸 JPG
```

### 6.6 job 级最终输出

当前 `finalizeDeliveryRun()` 会遍历整个 run。

建议补充 `jobId` 过滤能力：

```js
await finalizeDeliveryRunById(run.runId, {
  ...options,
  jobId: job.jobId
});
```

需要调整 `finalizeDeliveryRun()`：

```text
如果 options.jobId 存在，只处理该 job
如果 options.jobId 不存在，保持现有全 run 行为
```

这样完整交付可以做到当前 job 完成后立即输出：

```text
final-package/{job.folderName}/
  {baseName}_800x800.jpg
  {baseName}_1280x720.jpg
  {baseName}_1080x1920.jpg
```

## 8. 错误处理策略

### 8.1 可继续错误

这些错误只影响当前 job 或当前 target，不应停止整个 run：

| 错误 | 行为 |
| --- | --- |
| 单个 Legil target 生成失败 | 标记 target failed，继续当前 job 的其它 target 或下一 job |
| 当前 job 三尺寸不齐 | 当前 job 标记 failed 或 partial_finalized，继续下一 job |
| 单张源图读取失败 | 当前 job failed，继续下一 job |
| 单张图标准化失败 | 当前 job failed，继续下一 job |

### 8.2 应停止任务的全局错误

这些错误会影响所有 job，应停止任务等待人工处理：

| 错误 | 行为 |
| --- | --- |
| LOGO 模板目录不存在 | 停止完整交付 |
| 缺少某个目标尺寸 LOGO 模板 | 停止完整交付 |
| 输出目录不可写 | 停止完整交付 |
| Legil 登录失效 | 停止任务，提示人工处理 |
| 浏览器无法启动 | 停止任务 |

### 8.3 部分交付

第一版建议保留现有 `allowPartialPostprocess` 能力：

```text
如果允许部分交付：
  当前 job 能完成的 target 先输出
  job 标记 partial_finalized
  失败 target 留待后续补跑

如果不允许部分交付：
  当前 job 只要缺 target，就标记 failed
  继续下一 job
```

## 9. 断点恢复策略

恢复时按 job 粒度检查：

```text
for each job:
  if job.status is finalized:
    skip

  if final-package 中三个最终文件都存在且尺寸正确:
    mark job finalized
    skip

  if source-reuse target 缺失:
    根据源图比例重新补齐 source-reuse candidate

  if legil target 已有候选:
    复用已有候选

  if legil target 缺失或 failed:
    补跑该 target

  当前 job 三尺寸齐备后:
    只处理当前 job 的标准化和最终输出
```

恢复优势：

| 旧模式 | 新模式 |
| --- | --- |
| 全部 target 生成完才后处理，中断后前面已生成内容不一定可交付 | 每张图完成后已经有最终文件夹 |
| 恢复时容易重新扫大量 target | 恢复时直接跳过 finalized job |
| 失败定位偏 target 队列 | 失败定位到具体 OK 图和具体尺寸 |

### 阶段 1：源比例识别和 scan 阶段复用

目标：扫描 OK 图时自动识别源比例，并把匹配 target 初始化为 source-reuse。

开发内容：

```text
1. 在 store.js 中读取源图真实宽高
2. 新增比例匹配函数
3. 新增 source-reuse target 初始化逻辑
4. legil target 继续保持 pending
5. run.scan 中增加 sourceReuseTargetCount、legilTargetCount
```

建议新增 run.scan 字段：

```json
{

  "targetCount": 60,
  "sourceReuseTargetCount": 20,
  "legilTargetCount": 40,
  "estimatedSavedTargetCount": 20
}
```

验收标准：

```text
输入 1:1 图片时，800x800 target 为 source-reuse
输入 16:9 图片时，1280x720 target 为 source-reuse
输入 9:16 图片时，1080x1920 target 为 source-reuse
输入 4:3 图片时，三个 target 都是 legil
source-reuse target 不进入 Legil runnable tasks
```

### 阶段 2：前端展示源图复用计划

目标：页面清楚展示哪些 target 会复用源图，哪些 target 需要 Legil。

```text
每张 OK 图三个 target 的处理方式一眼可见
source-reuse target 不显示为“待生成”
```

### 阶段 3：完整交付改为 job 闭环执行

目标：完整交付模式从“全量 target 队列”改为“逐 job 闭环”。

开发内容：

```text
1. 新增 runDeliveryJobsClosedLoop()
2. 新增 runDeliveryJobClosedLoop()
3. 每个 job 内只对 legil target 调用 Legil
4. 当前 job 的 Legil target 完成后立即调用 job 级标准化
5. 当前 job 标准化完成后立即调用 job 级 finalize
6. 当前 job 完成后保存 run 并进入下一 job
```

验收标准：

```text
完整交付模式下，第 1 张 OK 图三尺寸完成后，final-package 中立即出现该图文件夹
不需要等待所有 OK 图的 Legil target 全部完成
source-reuse target 不调用 Legil
任务中断后，已 finalized job 保留最终交付文件
```

### 阶段 4：finalize 支持 jobId 过滤

目标：最终交付函数可以只处理当前 job。

开发内容：

```text
1. finalizeDeliveryRun() 支持 options.jobId
2. finalizeDeliveryRunById() 透传 body.jobId
3. job 级 finalize 后只更新当前 job 的 postprocess 状态
4. run 级 completedJobs/failedJobs 正确统计
```

验收标准：

```text
调用 finalize with jobId 只输出当前 job 文件夹
不会重复处理其它 job
已输出文件可被复用，不重复覆盖除非 force=true
```

### 阶段 5：断点恢复和补跑

目标：恢复时跳过已交付 job，只补缺失或失败尺寸。

开发内容：

```text
1. 恢复时识别 finalized job
2. 检查 final-package 中当前 job 三张最终图是否存在且尺寸正确
3. source-reuse target 缺失时可重新补齐
4. failed legil target 可补跑
5. “补跑此图”只补当前 job 缺失或失败 target
```

验收标准：

```text
任务中断后重新开始，不重跑已 finalized job
删除某个 job 的一个最终尺寸后，可补跑该 job
source-reuse target 不因为补跑而进入 Legil
```

### 阶段 6：测试和验收

目标：覆盖核心业务路径，保证稳定可用。

测试组合：

| 场景 | 期望 |
| --- | --- |
| 单张 `1:1` OK 图 | `800x800` 复用，另外两个尺寸走 Legil |
| 单张 `16:9` OK 图 | `1280x720` 复用，另外两个尺寸走 Legil |
| 单张 `9:16` OK 图 | `1080x1920` 复用，另外两个尺寸走 Legil |
| 单张 `4:3` OK 图 | 三个尺寸都走 Legil |
| 多张混合比例 OK 图 | 每张图按自身比例复用对应 target |

| LOGO 模板缺失 | 任务停止并提示全局错误 |
| source-reuse 标准化 | 源 OK 图能输出精确目标尺寸、JPG、体积合规 |

验收标准：

```text
最终每个 finalized job 都有三个目标尺寸文件
三个目标尺寸文件尺寸精确
三个目标尺寸文件均加 LOGO
三个目标尺寸文件命名正确
source-reuse target 没有 Legil 生成记录
完整交付按单图输出，不等待全量完成
```

## 12. 推荐实现顺序

最小可用版本建议按这个顺序做：

```text
1. scan 阶段源比例识别
2. source-reuse target 数据结构落盘
3. 页面展示源图复用计划
4. 确认 source-reuse target 不进 Legil 队列
5. 完整交付执行器改为逐 job 闭环
6. finalize 支持 jobId
7. 断点恢复和补跑
8. 自动化测试和真实样例验收
```

其中第 1-4 步先做完，就已经能节省 Legil target；第 5-7 步解决“完成一张交付一张”的流程体验。

## 14. 兼容性策略

### 14.1 历史 run

历史 run 没有 `generationMode`、`reuseSource` 字段时：

```text
如果 target 已有 candidates，则按原逻辑展示和处理
如果 target pending，则默认 generationMode=legil
重新扫描同一输入目录时，可按新逻辑补齐 source-reuse 信息
```

### 14.2 旧接口

保留现有接口：

```text
POST /api/delivery/scan
POST /api/delivery/start
POST /api/delivery/resume
POST /api/delivery/stop
POST /api/delivery/runs/:runId/standardize
POST /api/delivery/runs/:runId/finalize
```

新增行为尽量通过现有 payload 和 run 状态兼容，不先新增大量接口。

### 14.3 仅 Legil 模式

仅 Legil 模式也可以展示 source-reuse target，但不自动完整后处理：

```text
source-reuse target：显示源图复用，跳过 Legil
legil target：生成缺失比例候选
不自动加 LOGO、重命名、打包
```

## 15. 最终业务口径

新版三尺寸交付定义为：

> 对每张 OK 图逐张生成完整三尺寸交付包；源图已匹配的比例默认复用并跳过 Legil，其它比例由 Legil 适配，三尺寸齐备后立即完成标准化、加 LOGO、重命名和最终输出，再处理下一张。

这版调整不改变最终交付物要求，只优化生成路径和执行粒度：

```text
最终仍然是每张 OK 图一个文件夹
每个文件夹仍然有 800x800、1280x720、1080x1920 三张图
源图匹配比例时少跑一个 Legil target
完整交付完成一张输出一张
```
